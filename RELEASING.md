# Releasing Goleo to npm

Goleo ships **eight** npm packages, all under the `@goleo` scope:

| Package | What it is |
|---|---|
| `@goleo/bridge` | Frontend bridge library (TypeScript) |
| `@goleo/cli` | The `goleo` CLI (thin Node launcher) — includes `goleo new` scaffolding |
| `@goleo/cli-darwin-arm64` · `-darwin-x64` · `-linux-arm64` · `-linux-x64` · `-win32-arm64` · `-win32-x64` | Prebuilt CLI binaries, one per OS/CPU. Generated by `cli/npm/build-platform-packages.js`; `@goleo/cli` pulls the matching one via `optionalDependencies`. |

Steady-state releases are automated (tag → GitHub Actions → npm **trusted
publishing**, no token). The **very first** publish has a chicken-and-egg —
trusted publishers can only be attached to packages that already exist — so day
zero is a one-time manual bootstrap. Follow the sections in order.

Because every package is under `@goleo`, a token scoped to just that org is
enough — no unscoped-package permissions to worry about.

---

## 0. Prerequisites (once)

- **npm account**, logged in: `npm login` → verify `npm whoami`.
- **Own the `@goleo` scope.** On npmjs.com → *Add Organization* → name `goleo`
  (Free / public). This claims `@goleo`. (`npm org ls goleo` should list you as
  `owner`.)
- **Names are free.** `npm view @goleo/cli` should return **E404** (available).
- **Go toolchain** installed (day zero cross-compiles the six binaries) + Node 18+.
- Confirm the **LICENSE** holder (currently `Aaron Parker`).

---

## 1. Day zero — the first publish (creates all 8 packages)

Because a trusted publisher can't be configured until a package exists, do one
manual publish. Use a temporary token so 2FA/OTP doesn't block the eight
publishes.

```bash
# a) npmjs.com → Access Tokens → Generate New Token. A Granular token with
#    "Packages and scopes → Read and write" for the @goleo org (or a Classic
#    "Automation" token) is sufficient — everything is @goleo-scoped.

# b) Store it locally just for this bootstrap (writes ~/.npmrc):
npm config set //registry.npmjs.org/:_authToken=<TOKEN>

# c) From the repo root — build + publish everything:
npm install
npm run publish:all      # tsc bridge, bundle Go source, cross-compile 6 binaries,
                         # then publish: platform pkgs → @goleo/cli → @goleo/bridge

# d) Remove the token again (and optionally revoke it on npmjs):
npm config delete //registry.npmjs.org/:_authToken
```

Verify: `npm view @goleo/cli version` shows `0.1.0`, and on any machine
`npm install -g @goleo/cli && goleo version` prints `Goleo v0.1.0`.

> Starting version is `0.1.0` (all workspaces). To debut at `1.0.0` instead, run
> `npm version 1.0.0 --workspaces --no-git-tag-version` before step (c).

---

## 2. Enable trusted publishing (once, after day zero)

Now that the packages exist, wire up OIDC so future releases need no token.

1. **Make the GitHub repo public** (required for provenance).
2. For **each** of the eight packages: npmjs.com → *package → Settings → Trusted
   Publishing → Add a trusted publisher*:
   - Provider: **GitHub Actions**
   - Owner: **daforester**
   - Repository: **goleo**
   - Workflow: **release.yml**

No `NPM_TOKEN` GitHub secret is needed — `.github/workflows/release.yml` already
has `id-token: write` and upgrades to `npm@latest` for the OIDC exchange.

---

## 3. Every release after that (tag → automated)

Bump all workspaces to the same version, commit, tag, push:

```bash
npm version 0.2.0 --workspaces --no-git-tag-version   # bumps @goleo/bridge + @goleo/cli
git commit -am "release: v0.2.0"
git tag v0.2.0
git push --follow-tags
```

The six `@goleo/cli-<os>-<arch>` packages are **not** listed here — `@goleo/cli`
pulls them through `optionalDependencies`, and the committed values are deliberately
`"latest"`. They cannot be the exact version: a release commits `X.Y.Z` *before*
those packages exist on the registry, npm cannot write lockfile entries for a version
it cannot resolve, and because the dependencies are **optional** it drops them
silently rather than failing. That left `package.json` declaring six packages the
lockfile knew nothing about, so `npm ci` — which requires the two to agree exactly —
refused on a fresh clone with `Missing: @goleo/cli-darwin-arm64@X.Y.Z from lock file`.
It needed a manual re-lock after every single release, and it stayed invisible for a
long time because every workflow runs `npm install`, which re-resolves the tree rather
than verifying it.

`"latest"` always resolves, so the lockfile is consistent at every commit and there is
nothing to repair. `build-platform-packages.js` stamps the exact version into
`optionalDependencies` just before publishing, so what reaches the registry is pinned
as tightly as ever. `cli/npm/check-optional-deps.js` runs from `prepublishOnly` and
**refuses to publish** if it finds anything other than the exact version there — the
one thing that must never ship is a `"latest"` pin, which would leave end users with a
floating platform binary. CI additionally asserts that `npm ci` works at the root and
that the guard still rejects the committed tree.

The `release` workflow then:
1. cross-compiles the six platform binaries (`CGO_ENABLED=0`),
2. builds the `@goleo/cli-*` packages (their versions + `@goleo/cli`'s
   `optionalDependencies` are re-synced by `build-platform-packages.js`, same as
   the lifecycle hook above — this is what actually reaches the npm registry),
3. publishes **platform packages → `@goleo/cli` → `@goleo/bridge`** via OIDC,
   each with provenance.

You only set two versions; the platform packages inherit `@goleo/cli`'s.

## Windows code signing (optional, strongly recommended)

Unsigned Windows executables get flagged by reputation-based antivirus. This is
not theoretical: Bitdefender quarantined `@goleo/cli-win32-x64`'s binary
straight out of a user's `node_modules`, leaving `goleo` reporting *"no
prebuilt binary found"*. The published package was intact and carried SLSA
provenance — the heuristic simply distrusts a new, unsigned Go binary.

The release workflow signs both Windows binaries when a certificate is
configured, and skips with a notice when it isn't, so releases keep working
either way. To enable it, add two repository secrets:

| Secret | Value |
|---|---|
| `WINDOWS_CERT_BASE64` | the `.pfx`/`.p12` code-signing certificate, base64-encoded |
| `WINDOWS_CERT_PASSWORD` | its password |

```bash
# produce the base64 payload
base64 -w0 code-signing.pfx      # Linux/macOS
certutil -encode code-signing.pfx cert.b64   # Windows, then strip the header/footer lines
```

Signing uses `osslsigncode`, not `signtool`: the release job cross-compiles
every target from one Linux runner, and signtool is Windows-only.
`runtime/signing.go`'s `signWindows` is the separate, signtool-based path that
signs *apps built with goleo* on a Windows machine — the two don't overlap.

Signatures are RFC 3161 timestamped (`timestamp.digicert.com`), so they stay
valid after the certificate expires.

A certificate has to come from a CA — a self-signed one adds no reputation and
will not stop the flagging. EV certificates carry the most weight with
SmartScreen; standard OV certificates still help substantially.

## Manual release (fallback)

Needs the Go toolchain and npm auth (a token in `~/.npmrc`, as in day zero):

```bash
npm run build:all      # tsc bridge + bundle Go source + build platform packages
npm run publish:all    # platform packages, then @goleo/cli, @goleo/bridge
```

## What users run after a release

```bash
npm install -g @goleo/cli        # installs the matching @goleo/cli-<os>-<arch> automatically
goleo new my-app                 # scaffold a project

# …or with no global install:
npx @goleo/cli new my-app
```
